# プロジェクト開発ルール

## 0. 禁止事項（絶対厳守 / 最優先）

- **ユーザーの明示的な指示なしに git の履歴・作業ツリーを変える操作を行わないこと。**
  - 禁止: `git commit` / `git push` / `git checkout -b` などのブランチ作成・切替 / `git reset` / `git stash` / `git rebase` / `git merge` / `git add`
  - 可: `git status` / `git diff` / `git log` / `git show` などの読み取り
  - 「コミットして」「push して」と明示された場合のみ、その操作だけを行う。コミットの承認は push の承認を含まない。
- ユーザーの承認なしにファイルを編集しないこと（3 章）。
- テストを削除・スキップして「通した」ことにしないこと（4 章）。
- 資格情報・アクセストークン・VIN・位置情報などの個人情報をコード・ログ・テストデータ・コミットに残さないこと。

## 1. 全体原則

- 回答はすべて**日本語**で行ってください。
- 常にシニアエンジニアとして、丁寧かつ簡潔に回答してください。

## 2. 開発プロセス（必須ステップ）

新しい機能の実装や大きな修正を行う際は、必ず以下の3ステップを順に踏んでください。

### ステップ1: ブレインストーミング (`superpowers:brainstorming`)

- 実装を始める前に、要件の意図や背景を確認してください。
- 技術的な選択肢（メリット・デメリット）を提示し、影響範囲を洗い出してください。
- ユーザーから実装方針の合意を得るまで、コード生成は開始しないでください。
- 不明点は必ず確認してください。仮定で進めてはなりません。
- 積極的に機能の改善案やリスク回避策も提案してください。

### ステップ2: 計画作成 (`superpowers:writing-plans`)

- 合意した方針に基づき、詳細な実装計画を作成してください。
- 変更が必要なファイル、手順、依存関係を箇条書きで示してください。
- 可能であれば、コードの構造や関数の概要も説明してください。
- 図を用いて説明することも有効です。必要に応じて、コードスニペットを使って具体例を示してください。

### ステップ3: 実装 (`superpowers:subagent-driven-development`)

- 作成した計画に基づき、コードを生成・修正してください。
- 可能な限り、テストコードの作成や既存テストの実行も含めてください。
- 変更内容を報告する前に、コードレビューの観点で自己チェックを行ってください。

## 3. 作業前の変更提案（絶対厳守）

いかなる実装・修正・削除作業を行う前にも、必ず以下を提示してユーザーの承認を得ること。承認前にファイルを編集してはならない。

- **変更対象ファイル**: 変更するファイルの一覧
- **変更概要**: 各ファイルに対して何を追加・変更・削除するかの箇条書き
- **影響範囲**: 変更によって影響を受ける可能性のある他のコンポーネントや機能

ユーザーが「OK」「進めて」「実装して」などの承認を明示した後にのみ、実装を開始すること。

## 4. 編集後の必須確認（絶対厳守）

コード変更後は必ず以下をすべて実行し、エラーがないことを確認すること。

### 4-1. 環境準備（初回のみ）

- Python は `.tool-versions` の版（3.11 系）を使う。
- `python -m venv .venv` → 有効化 → `pip install -r requirements.test.txt`

### 4-2. テスト

- ルートで `python -m pytest tests`
  - 日産の BFF / KAuth など**外部サービスへ実際に接続する処理はテスト対象にしない**。`requests` / OAuth セッションは `MagicMock` 等でモックし、レスポンスの解釈や状態遷移は副作用のない関数・メソッドに切り出してテストすること。
  - テストは `tests/` 配下に置き、`test_<module>.py` の命名に従う（既存: `test_kamereon_jp.py` `test_sensor.py` など）。
  - `pytest_homeassistant_custom_component` の `hass` フィクスチャを使う HA 層のテストと、`kamereon` パッケージ単体のテストを混ぜない。

### 4-3. 静的検証

- `manifest.json` / `hacs.json` / `translations/*.json` を変えた場合は JSON として妥当であることを確認する（CI の hassfest / HACS 検証で落ちる）。
- 構文エラーの早期検出には `python -m compileall -q custom_components` を使ってよい。

### 4-4. 実行時のルール

- **テストがすべてパスすることまで確認すること。**
- 失敗した場合は、原因を特定して修正するか、修正できない場合は失敗内容をそのまま報告すること。テストを削除・スキップして通したことにしてはならない。
- 不具合を修正した場合は、**その不具合を再現する回帰テストを追加すること**（修正前のコードで失敗し、修正後に成功することを確認する）。
- 確認せずに完了報告をしてはならない。結果（件数・成否）を報告に含めること。
- ローカルに Python 3.11 / pytest が無くテストを実行できなかった場合は、その旨を隠さず報告すること。

## 5. 技術スタック & コーディング規約

- 言語: Python 3.11（Home Assistant 2023.11 以降で動作すること。`hacs.json` の下限を参照）
- フレームワーク: Home Assistant カスタム統合（`DataUpdateCoordinator` ベース、`config_flow` あり）。HTTP は `requests` + `requests_oauthlib`
- テスト: pytest / pytest-asyncio / pytest-homeassistant-custom-component
- 命名規則: 変数・関数・モジュールは snake_case、クラス・Enum は PascalCase、定数は UPPER_SNAKE_CASE
- **ファイルを実装する前に、必ず `.claude/instructions/` 配下の該当言語の instructions ファイルを読み、全ルールを遵守すること。（Python → `python.instructions.md`）**
